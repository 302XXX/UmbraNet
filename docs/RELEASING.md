# Обновления и подготовка первого релиза

## Что меняется в этой ветке

- `install.bat` устанавливает зависимости из `requirements.txt`, без legacy `pydivert`.
  Действующий DPI — поставляемый `bin/winws.exe` и его файлы WinDivert.
- Прямые зависимости закреплены через `==`. `constraints.txt` фиксирует также
  транзитивные runtime-зависимости. Это фиксация версий, не lock с хешами файлов.
  Инструменты bootstrap (`pip`, `setuptools`, `wheel`) установщик пока обновляет.
- В `engine_adapter.py` и `dns_server.py` диагностируются 39 прежде пустых
  обработчиков. Ожидаемые `_queue.Full` и `_SkipRecord` оставлены без шума.
  Одинаковая операция логируется не чаще раза в минуту; текст исключения не
  выводится, чтобы не раскрывать домены, токены и пароли из URL.
- Цикл `BogusUpdater` ведёт независимые сроки для bogus-IP, подписок и доменных
  кэшей стратегий: сразу при запуске, затем раз в 24 часа после успеха, через час
  после ошибки. Сроки монотонные, в памяти текущей сессии. Приложение не обязано
  быть перезапущено для очередного обновления.
- GUI запускает этот же цикл с задержкой 3 секунды; headless-путь — при успешном
  запуске DNS. Остановка движка останавливает цикл, следующий запуск возобновляет
  его. Завершающийся сетевой запрос может закончиться после `stop()`; следующие
  задания не начинаются. При быстром Stop/Start не создаются два планировщика.
- Ручное обновление подписок не пересекается с автоматическим. При ошибке хотя бы
  одного источника или изменении настроек во время загрузки остаётся старый кэш.
  Пустой/невалидный ответ не очищает рабочий список; явное удаление всех подписок
  очищает его. Запись кэшей атомарная.

### Важно: списки стратегий не равны параметрам стратегий

Текущий `StrategyManager` берёт DPI-цели только из выбранных пользователем доменов
и подписок. `remote_hostlist_*` им не используются. Если в JSON явно указан
`remote_url`, фоновая задача обновляет только соответствующий доменный кэш;
она не заменяет JSON, аргументы WinWS или пользовательские цели. В поставляемой
Uz1 `remote_url` отсутствует, поэтому эта задача не делает сетевых запросов.

Обновлённые подписки применяются к DNS-маршрутизации в памяти. DPI-hostlist
собирается при следующем запуске/применении режима существующим механизмом.
Фоновый updater **не перезапускает WinWS**.

## Проверка новых версий программы

`core/update_checker.py` обращается только к GitHub Releases репозитория
`302XXX/UmbraNet`. Никаких автоматических скачиваний исполняемых файлов,
замены программы или запуска установщика нет.

- Фоновая проверка при открытии программы и затем раз в 24 часа.
- Повтор через час при сетевой ошибке или лимите GitHub API.
- Таймаут запроса 10 секунд, ответ ограничен 2 MiB; не требуется GitHub-токен.
- По умолчанию только стабильный канал (`releases/latest`). Тестовый канал
  включается явно во вкладке «О программе», настройка сохраняется локально.
- Тестовый канал рассматривает последние 100 опубликованных записей GitHub.
- Короткие версии разбираются в `core/app_version.py`, сравнение — через
  `packaging.version.Version`: `26.0.1a < 26.0.1b < 26.0.1r < 26.0.2a`.
  Старые dev/rc/plain-теги поддерживаются. Draft-релизы и невалидные теги пропускаются.
- Пока релизов нет, UI сообщает об этом, а не об ошибке установки.
- Результат и кнопка «Открыть страницу релиза» — в «О программе»; при наличии трея
  новая версия также вызывает однократное уведомление за сессию.
- Ссылка строится на HTTPS-страницу этого репозитория, а не берётся из `html_url`
  удалённого ответа. Браузер открывается только по нажатию пользователя.

## Обновление зависимостей

Базовая целевая среда: Windows x64, Python 3.10–3.14. Текущие pins нужно
подтвердить в чистом Windows-окружении перед релизом. Разрешение pip для Windows
не является проверкой запуска DLL, GUI, драйвера или DNS.

1. Менять прямые pins в `requirements.txt` осознанно, вместе с транзитивными
   pins в `constraints.txt`; проверять требования к Python и наличие Windows wheels.
2. Создать чистое окружение, установить оба requirements-файла и выполнить
   `python -m pip check`.
3. Проверить тесты на Linux и Windows для Python 3.10, 3.12, 3.13, 3.14 (матрица CI).
4. В Linux нужны библиотеки Qt из шага CI; пропущенные GUI-тесты из-за отсутствия
   `libGL` нельзя засчитывать как успешную проверку интерфейса.
5. Не копировать в constraints весь `pip freeze` рабочего окружения: там могут
   быть несвязанные зависимости. Сохранять только runtime dependency closure.

## Обозначения версий

Единственный источник текущей версии — `umbranet/__init__.py`: **`26.0.1b`**.
Она отображается без преобразования в `b0` во вкладке «О программе», отчётах
и уведомлениях об обновлении. Это **бета**, не стабильный выпуск: дополнительные
исправления программы запланированы после слияния текущей работы.

| Суффикс | Стадия | Пример тега GitHub |
| --- | --- | --- |
| `a` | Альфа | `v26.0.1a` |
| `b` | Бета | `v26.0.1b` |
| `r` | Стабильный релиз | `v26.0.1r` |

Сначала сравниваются три числовых компонента, затем стадия `a < b < r`.
Например, `26.0.2a` новее `26.0.1r`, но видна только в тестовом канале.
Для следующей отличающейся бета-сборки нужно увеличить номер (например, `26.0.2b`),
а не заменять файлы уже опубликованного тега: одинаковые версии обновлением не считаются.

Внутри `a`/`b` соответствуют PEP 440 `a0`/`b0`, `r` — обычной стабильной версии
без суффикса. Нельзя передавать `26.0.1r` прямо в `packaging.Version`: библиотека
понимает `r` как post-release, а не как наш маркер релиза. Поэтому UpdateChecker
использует общий разборщик. `26.0.1r` и старое обозначение `26.0.1` эквивалентны
при сравнении; ложного уведомления об обновлении между ними не будет.

Альфа/бета скрыты из стабильного канала даже при ошибочно снятом признаке
`prerelease` в GitHub. Для просмотра новых бет пользователь явно включает
тестовый канал в «О программе»; сама установка беты эту настройку не меняет.

## Перед публикацией беты

Изменение версии не публикует тег или GitHub Release и не сливает PR.
Публикация и слияние — отдельные согласованные действия.

Перед первым релизом:

- [ ] Зелёная Windows/Linux матрица CI для выбранного коммита.
- [ ] Чистая установка через `install.bat` на Windows x64, `pip check` без ошибок.
- [ ] Запуск GUI, узкое окно «О программе», проверка обновлений без зависания UI.
- [ ] DNS: UDP/DoH/DoT/DoQ/DNSCrypt, offline-старт, Stop/Start, восстановление
      системного DNS при выходе.
- [ ] DPI/Combo: запуск поставляемого WinWS без установленного pydivert.
- [ ] Подписки: ручное/фоновое обновление, ошибка источника не стирает кэш;
      параметры пользовательских стратегий не меняются.
- [ ] Проверить `umbranet/__init__.py`: текущий выпуск — `26.0.1b`.
      Менять `b` на `r` только после отдельной приёмки стабильного выпуска.
- [ ] Подготовить описание релиза, состав архива и инструкции установки.
- [ ] При согласованной публикации использовать тег `v26.0.1b` и обязательно
      отметить GitHub Release как **prerelease**, строго на проверенном коммите.

Для бета-выпуска тестовый канал UpdateChecker нужно включить явно. Одна лишь
публикация Git-тега без GitHub Release не делает его видимым проверке обновлений.

## Исправление установки на Python 3.14

Предыдущий pin `PySide6==6.9.3` имел `Requires-Python: <3.14,>=3.9`.
Установщик при этом пропускал любой Python >=3.10. На Python 3.14 pip сообщал
`ResolutionImpossible` / `no matching distributions`, хотя requirements и
constraints требовали одну и ту же версию. Длинный путь здесь не был причиной.

- Qt-комплект (`PySide6`, Essentials, Addons, `shiboken6`) закреплён на **6.10.3**:
  его метаданные допускают Python 3.14 (`<3.15,>=3.9`). Остальные runtime-pins сохранены.
- Перед созданием окружения и перед любой установкой пакетов проверяется обычный
  **CPython 3.10–3.14 для Windows x64**, с GIL. Неподдерживаемые интерпретаторы
  завершают установщик с объяснением до запуска pip.
- Уже существующая `.venv` имеет приоритет: проверяется её Python, а не случайная
  другая системная версия. Окружение автоматически не удаляется и не пересоздаётся.
- Runtime-пакеты устанавливаются только из wheels; bootstrap также учитывает
  constraints, чтобы не менять runtime-pins неявно. Перед сообщением «Готово»
  выполняются `pip check` и импорт `QtCore`, `QtGui`, `QtWidgets` (включая Qt DLL).
- Ошибка pip больше не объясняется автоматически длинным путём: подсказки разделены
  для несовместимости, сети и реальной ошибки пути.
- CI включает Python 3.14 на Linux и Windows; Windows 3.14 дополнительно прогоняет
  настоящий `install.bat` дважды на заранее созданной `.venv`.

Для повторной установки после описанного сбоя нужно обновить всю копию ветки,
включая `requirements.txt`, `constraints.txt`, `install.bat` и
`tools/check_install_python.py`. Подходящую `.venv` на обычном Python 3.14 x64
удалять не требуется: повторный `install.bat` установит исправленный Qt-комплект.
`UMBRANET_INSTALL_NO_PAUSE=1` отключает ожидание клавиши для автоматических проверок.

Разрешение Windows-wheels через pip не заменяет реальный запуск установщика и
GUI на Windows. Успех локальных headless-тестов также не закрывает ранее выявленные
GUI-ошибки PR; их проверка остаётся отдельным пунктом приёмки.
